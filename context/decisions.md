# decisions

## native-migration

### [2026-11-11] 转原生 Android：档位选型（走 B3 全量迁移） (src: 用户)

**场景/痛点**：拾光是 Flutter Android app（`lib/` 116 文件 / 35,524 行）+ 内嵌 MCP 服务端（MCP 100% 跑在 Dart VM，由 goodhub 跨进程拉起的 headless FlutterEngine 承载）。诉求为「彻底摆脱 Flutter」。同期 V1.5 候补（通知 / 日历拖拽 / 周月视图 / Markdown 导出）与协同五阶段施工序均未完成，且为单人项目（唯一作者，近 30 天 20 次提交）——全量迁移意味着 12–18 人月的功能冻结。

**可选方案**：

- `B0` 维持 Flutter + 局部减负（替换 3 个高风险平台插件）：5–8 人日，零功能冻结。**否决理由**：不回应「摆脱 Flutter」这一诉求本身，只降低插件升级风险。
- `B1` 仅做 P0 契约固化与黄金向量：10–15 人日，无条件成立但非终态。**否决理由**：单独投入不构成对诉求的完整回应，但可作为 `B3` 的第一阶段并入。
- `B2` P0+P1（MCP 内核平移 + 原生内核接入）：22–33 人日。**否决理由**：产生「原生内核 + Flutter UI」混态，两套实现长期并存必然漂移（R7），不可作为终态交付；其边际收益低于直接推进 `B3`。
- `B3` 全量迁移 P0–P5：242–353 人日 / 12–18 人月。**采纳**。

**最终决定**：走 `B3`。以 `P0` 契约固化（黄金向量 + DDL 冻结 + relay proto 双副本收敛）前置，`G0`/`G1`/`G2` 三道决策门递进，`G2` 为唯一止损点（内核平移守住预算与信心才继续 `P3`/`P4`）。方案、成本与风险明细见 `docs/design/native-migration.md`；任务拆解落 `context/epics/native-migration/todos.md`。

**AI 洞察**：

- 决策之所以成立，是因为项目架构自带迁移接缝——`coding-standards.md` §1 的「无头系统」原则 + `arch-guard` R1–R6 机械守护，使 UI 层已是纯呈现层（`lib/ui/` 对数据层仅 10 个读方法 + 17 处订阅，写全走命令面）。这是早先「轴 B 纯 Dart 化」的存量投资，不是运气。
- 真正的风险不在 UI 视觉细节：A 类 tokens（`tokens.dart` 155 行）已是独立于 Flutter 的纯数值常量，配合规范 SSOT 与 debug 桥已有的整屏截图能力（可做像素基线），视觉细节基本不丢。风险集中在三类**静默失败**的线级契约——E2EE 封装字节级（Argon2id 在 Kotlin 需 BouncyCastle，JCA/Tink 均无）、relay protobuf wire format、goodhub AIDL 语义（`_async` 占位帧 + `onEvent` 终帧 + 三个错误码）。这三类错了不报错，只能靠 `P0` 黄金向量挡住。
- 成本估算经历一次上修：P4 UI 自顶向下估 90–140 人日，按「设计系统 + 组件族 + 主干页 + 浮层族 + 协作页 + 设置引导 + 基线基建 + 走查」自底向上拆解为 120–175，总成本由 212–318 上修至 242–353 人日。教训：「按规范重画」与「按代码翻译」两种口径混用时必须用后者自底向上校准，前者系统性低估。

### [2026-11-11] 转原生 Android：四项未决事项拍板（发布档 / Dart 参考实现 / 像素基线窗口 / 新需求冻结） (src: 用户)

**场景/痛点**：`docs/design/native-migration.md` §10 留了 4 项待决——`P4` 是否做骨架级过渡发布、Dart 侧是否留作 relay 契约参考实现、像素基线采集窗口、迁移期是否冻结新需求。四项都直接决定 12–18 人月窗口的工期结构与留存风险，留到施工期再定会让「边做边改口径」吃掉工期。

**可选方案**：

- 未决 1：`P4` 内部分两级交付（骨架级 → 规范级）→ **否决**：骨架级一旦对外发布，即损害日历拖拽手感、浮层阻尼、动效呼吸感这类用户最敏感的体验，中间态既损留存又拉长工期。
- 未决 1（采纳）：按模块逐个在内部达成规范级后再端到端合流，整包交付。
- 未决 2：Dart 侧 `P5` 后即退 → **否决**：`P2` relay 契约联调期没有第二实现可比对，协议断言失败只能读码猜。
- 未决 2（采纳）：保留至 `P5` 前夜——`P0` 打 tag 或归档 `legacy-reference/` 保持可编译，`P2` 用 Dart 与 Kotlin 双客户端连本地 mock-server 抓包对拍。
- 未决 3：等到 `P3` 期间再采 → **否决**：`P2`/`P3` 的依赖重构与 Gradle 升级一旦破坏 Flutter 编译环境，采图从顺手做变成额外负担。
- 未决 3（采纳）：前移至 `P0` 末期–`P1`，趁当前工程稳定可跑即采完「20 页 × 典型状态」存档。
- 未决 4：按 `G0` 结果再定冻结口径 → **否决**：口径悬着的代价是持续开放「看似轻微」的只读需求变更，每项都要在 Dart 测试 / 黄金向量 / Kotlin 实现三处同步。
- 未决 4（采纳）：无条件绝对冻结，唯一开口是阻断施工或决策门判定的缺陷修复。

**最终决定**：四项全部按采纳方案拍板。留痕：native-migration.md §10（决定 1–4），并回改 §3.1 成本时序、§8（`P4` 发布档约束 + 像素基线采集窗口）、§9 测试形态；schedule-app.md §11 拍板台账新增四行（`P4` 发布档 / Dart 参考实现存续 / 像素基线采集窗口 / 迁移期新需求冻结）；任务拆解落 context/epics/native-migration/todos.md。

**AI 洞察**：

- 四项决定的共同形状是「把不确定性成本前置 + 冻结开口」：像素基线前置是用一次性投入买下「细节丢失可度量」，Dart 侧保留是买下「协议失败可定位」，发布档约束与需求冻结是砍掉「中间态交付」与「范围蠕变」两条工期放大器。
- 决定 3 有个被低估的正向副作用：基线入库后，「页面 × 状态」枚举会同时成为 `P0` 黄金向量的状态清单与 `P4` 像素 diff 的对照集——状态穷举从 `P4` 的一道工序提前成一份可复用清单资产。
- 决定 4 的真实成本不在工期而在注意力：单人项目里「顺手加的只读需求」会持续打断主线上下文重建，与 R8（知识断层）叠加放大。
- 遗留两点需在 `G0` 复核算时回补：像素基线前置把 `P0`/`P1` 各推高约 2–5 人日（总量估算不变，仅时序前移）；「页面 × 状态」枚举范围仍需在 `P0` 内定稿，否则采图范围会继续漂。

### [2026-11-11] 转原生 Android：AI 辅助施工规程采纳与六处修正 (src: 用户)

**场景/痛点**：迁移期主产出由 AI 生成，风险不是「写不出代码」而是两类静默劣化——把 Flutter 的框架隐式妥协（控件默认度量、SnackBar 固定时长、Stack loose fit、build 内副作用、`animateTo` 对齐语义）照搬成畸形原生代码；以及在「顺手现代化」中改动可观察语义（把 FIFO 写锁换成无序并发、把 CAS 冲突策略改成覆盖写）。用户提出一整套「把 AI 从代码翻译器变为规范编译器与契约验证器」的方案：工程级 Agent 规则、两通道输入的施工流、Konsist 架构测试、像素自动化回归。

**可选方案**（逐项判定）：

- 工程级 Agent 规则文件（`.cursorrules` / Agent Instructions）→ **修正后采纳**：不新建第 4 份规则源（本项目已有 `AGENTS.md` + 项目 skill + `coding-standards.md`）；规则落人类事实源 + AI 入口 + 机器脚本三处单向引用。
- 状态提升 / Composable 纯函数化 / UI 禁直连数据层 → **全量采纳**：与 `arch-guard` R1 / R5 同构，Kotlin 侧照抄正则。
- Tokens 先行注入、禁魔数 → **全量采纳**（性价比最高）：`tokens.dart` 155 行零 Flutter 依赖，Kotlin 侧正则可查裸 dp/sp。
- `UiEvent` sealed 全量 MVI → **修正后采纳**：分档——有状态机的页用 `UiState + UiEvent`，简单页用 hoisted state + lambda；否则事件通道传大对象踩 stability 陷阱。
- 「生成时不输入 Flutter 源码」→ **修正后采纳**：改双通道——生成通道禁读实现体，校验通道只读**行为清单**（手势竞技场仲裁顺序、三层浮层嵌套只存在于 Flutter 代码，不在规范里）。
- AI Fuzzing 扩充边界向量 → **修正后采纳**：AI 只能**提候选**，人工确认语义后才准固化。
- Konsist 架构测试 → **采纳但延后**：需完整 Kotlin 源码集，`P4` 起生效，不能当 `P0` 的守门员。
- 像素自动化回归（含 Roborazzi + 全局 0.5% 阈值）→ **修正后采纳**：基线固定设备与 DPR；Roborazzi 走 layoutlib 渲染，与真机 Skia 的字体 hinting / 阴影差异会产生大批假差异，故须同介质真机采图；全局阈值改分区阈值 + 文字区结构断言。
- 「运行现有 debug 端点即可建立基线库」→ **修正**：现端点只截当前整屏、无页面驱动、尺寸随机身 DPR，须先补采集器（导航驱动 + 状态注入 + 固定尺寸）。

**最终决定**：按上述修正后版本采纳，落 `docs/design/native-migration.md` 新增 §9.1「AI 辅助施工规程（人机分工与机械防线）」——两通道输入 / 禁止清单七项 / Kotlin 侧双层护栏（`arch-guard-kotlin` 六条正则 + Konsist 四条类型规则）/ 像素 diff 规格 / 黄金向量语义评审闸门 / 成本与门禁 / 速查表。成本增量 `P0` 5–8 人日、`P4` 3–5 人日，总量 242–353 → **250–366 人日**（12–18 人月口径不变）；§3.1 成本表、§6 档位表、§8 人日口径与 schedule-app §11 同步回写。

**AI 洞察**：

- 原方案约七成内容是 `native-migration.md` §8 / §9 既有口径的复述（规范编译、tokens 单一事实源、像素基线、黄金向量对拍），真正的增量是「从口径到机械执行」的三段：Kotlin 侧机械护栏、像素 diff 自动化管线、AI 施工规程本身。把它当全新策略会低估成本、也会漏掉真正的缺口。
- 最危险的一处是「对拍自证闭环」：向量由 AI 从 Dart 测试提取、实现也由 AI 生成，两端共享同一误解时对拍会全绿。**对拍只能证明一致，不能证明一致地正确**——语义评审是唯一破环点，必须写成流程闸门而非口头提醒。
- 像素 diff 的**介质一致性**最易被忽略：Roborazzi / Robolectric 走 layoutlib，与真机 Skia 在字体 hinting、阴影模糊上有系统性差异。文字区改结构断言（内容 + 基线 y + 行盒高 + 字号）比调像素阈值更根本。
- 规则必须有脚本化载体才有约束力：prompt 层规则会漂移并演化成新的「隐式妥协」。本项目 `arch-guard` 的 `--json` 单行结论 + `--self-test` 金丝雀 + `pre-commit-gate` 分派三件套是已验证的范式，Kotlin 侧照抄即可，无需引入新工具体系。
- 「现代化陷阱」是框架隐式妥协的镜像：FIFO 写锁 + 乐观锁 CAS 属契约语义，AI 在改写时极易顺手换成无序并发或覆盖写——这类劣化不报错，只能靠禁止清单 + 黄金向量双重挡住。

### [2026-11-11] 转原生 Android：G2 单向阀拍板与六项口径统一 (src: 用户)

**场景/痛点**：第二轮评审暴露五处深水区（SQLite 并发、时钟触发、proto presence、Compose 原生差异、止损机制），其中两处必须拍板才能收敛：① `G2` 不通过时到底交付什么——§7 原写「交付原生 MCP + Flutter UI 混态产品」，与「彻底摆脱 Flutter」的初心冲突；② proto runtime 三处口径矛盾（§2.4「protobuf-java + Wire」/§6「Room + Wire」/§9「Wire/kotlinx」，而 kotlinx-serialization 根本不消费 `.proto`）——runtime 不定案，字节级黄金向量根本无法生成。

**可选方案**：

- `G2` 不通过 → 对外发布混态产品 → **否决**：同时背负两套运行时的维护债务与发版包体积惩罚，且违背「彻底摆脱 Flutter」的初心；向用户交付残血半成品的侥幸空间必须物理切断。
- `G2` 不通过 → 正式回退 `B0`/`B1`，混态仅内部归档参考、绝不对外发布 → **采纳**。
- `G2` 通过后立即删除已平移的 Dart 逻辑 → **否决**：与 §10 决定 2「Dart 保留至 `P5` 前夜」直接冲突，删早就没有对拍回归基准；改为 `G2` 后 Dart 侧绝对只读（仅抓包对照），物理删除仍在 `P5`。
- proto runtime → Wire → **否决**：proto3 `optional` presence 与 unknown field 保留策略与 Dart 侧 `protobuf` 插件存在差异，正是字节级向量最易失配处。
- proto runtime → kotlinx-serialization → **否决**：不消费 `.proto`，口径本身是错的。
- proto runtime → **protobuf-javalite** → **采纳**：与 Dart 侧 `protobuf` 插件的 proto3 wire format、presence 规则同构。

**最终决定**：六项一并落盘——① `G2` 定为唯一且最后的单向阀（§1 结论 + §7 mermaid 与门禁表 + §10 决定 5 + schedule-app §11 新增行）；② proto runtime 定案 protobuf-javalite（§2.4 / §6 / §9 三处口径统一 + §11 新增行 + `P0` 三组字节级边界向量：空消息 / 含默认值标量 / 含未知字段的向前兼容消息）；③ SQLite 机制定性由「跨进程」纠正为**同进程多写者**（`ShiguangMcpBinderService` 无 `android:process`），缓解三条并列：Kotlin 侧单线程写队列（Room `transactionExecutor` + 单线程协程分发器）/ 双轨期 Dart 侧长事务分片 / `busy_timeout=5000` 严禁下调，写事务持锁阈值由 `P0` 实测固化而非预设 100ms（§4 `R3` + §9 双轨数据行）；④ 时钟基建（`TimeProvider` + 运行时注册 `ACTION_TIME_TICK` / `ACTION_TIME_CHANGED` / `ACTION_TIMEZONE_CHANGED` + `ON_RESUME` 前台恢复重算作息日）——真实缺口是日切只有冷启动 `dailyCutIfNeeded()` 触发，常驻后台过夜或改时钟后界面停在昨天；基准时间向量钉五个注入时刻，**剔除闰秒**（`java.time` 与 Dart `DateTime` 均为 POSIX，闰秒不存在）（§8 `P0` + §8 `P2` + §9.1.2）；⑤ 丢失点表由七项扩为九项（#6 扩充 IME 避让、#8 手势抢占与预测性返回与返回栈层级、#9 进程查杀与 Activity 重建恢复）（§8 + §9.1.4）；⑥ 时间盒与复盘闭环（`P0`/`P1` 各 ≤ 25 个工作日，超期 30% 强制复盘且产出必须三选一闭环）+ 内部 dogfood 构建走独立 `applicationId` 与独立 SQLite 文件（严禁与正式库共写）（§3.1 + §7 + §9）。成本由 250–366 上修至 **257–379 人日**（12–18 人月口径不变）。

**AI 洞察**：

- 本轮最重要的产出不是新增规则，而是**消解口径冲突**：proto runtime 的三处矛盾在文档里潜伏了整轮评审，直到要做字节级向量才暴露——runtime 不定案，「黄金向量」这一层根本建不起来。文档里的「三处同写一件事」是最易藏矛盾的形状。
- 「回退 `B0`/`B1`、混态仅内部归档」比「交付混态产品」多保住一样东西：`P0`/`P1`/`P2` 的黄金向量与原生代码资产在回退后仍是可复用的知识资产——回退不是清零。
- 时钟缺口暴露了一个通病：项目已有 `scheduleDayOf` 纯函数与向量对拍机制，但**「何时调用」从来不在向量覆盖范围内**。纯函数 + 注入让计算正确，广播与生命周期才让界面正确——后者才是真实故障面。
- ViewModel 的表述值得记一笔：进程未被杀时 ViewModel 在后台存活；「不保留活动」destroy Activity → `ViewModelStore` 清空 → ViewModel 丢失；真正进程被杀只能靠 `SavedStateHandle`。三条路径的验收动作不同，混成一条会漏测。
- 「跨进程死锁」的定性错误提示了一条通用纪律：迁移动作的风险描述必须回到**本仓事实**（Manifest 无 `android:process` 即同进程），通用框架知识不能替代仓库实测——与 §2.1「全文现状结论均为对仓库的实测值」是同一条纪律。

### [2026-11-11] 转原生 Android：动效物理参数定案与基线状态矩阵定稿 (src: 用户)

**场景/痛点**：§9.1 落地后暴露两个规范缺口——① 动效只有时长没有物理参数：`tokens.dart` `StMotion` 仅三个时长常量，曲线控制点与弹簧 damping/stiffness 全缺，`ui-design` §3.3 只写「250ms spring 单次」；② 像素基线的「页面 × 状态」枚举无权威出处（`ui-pages` §8 原有 4 条全局空态文案），而 §10 决定 3 要求枚举在 `P0` 内定稿。

**可选方案**：

- 弹簧参数由 AI 按「原生手感更佳」自行选择 → **否决**：撞 §9.1.2 魔数禁止项与「曲线逐位搬运」口径，且手感无判据。
- 弹簧参数与曲线对象落 Kotlin 侧 `StMotion`（含 `CubicBezierEasing`）→ **否决**：SSOT 污染到目标平台，Dart 侧与文档与实现脱节，且丢掉 A 类 token「零依赖逐字翻译」的无损性质。
- SSOT 留 `tokens.dart` `StMotion` 纯数值、Kotlin 侧逐字翻译 → **采纳**。
- 「250ms spring」字面落地 → **否决**：Compose `spring()` 不接受时长参数（时长由物理决定），字面语义在目标框架无对应参数。
- 保留弹簧物理 + 250ms 改写为「名义感知时长 ≈250ms」 → **采纳**。
- 状态矩阵按草案 60 组（2 高危 + 6 协作 + 12 基础）→ **否决**：分母算错——实际 30 个 UI 单元（`lib/ui/` 20 主页 + `collab/` 10 子页），其中协作是 9 页、另有 5 个组件/外壳单元；草案漏采 10 个协作页与全部组件外壳。
- A 档 S4 手势中间态进采图清单 → **否决**：瞬时态不可静态化（每帧在动、基线比对无稳定语义）→ 转交互对拍断言。
- 按 30 个 UI 单元逐一归属重建矩阵 → **采纳**，得 **84 组**静态基线。

**最终决定**：① 动效物理参数定案：阻尼 **0.75** / 刚度 **400**（= Material 3 `motion.spring.default`），安全线点亮表述改为「spring 单次，名义感知时长 ≈250ms」；三条曲线控制点（ease-out `Cubic(0,0,0.58,1)` / ease-in-out `Cubic(0.42,0,0.58,1)` / fast-out-slow-in `Cubic(0.4,0,0.2,1)`）与弹簧参数以 `tokens.dart` `StMotion` 纯数值为单一事实源，Kotlin 侧逐字翻译；`ui-design` §3.3 同步改写并指向 token。② 基线状态矩阵定稿 **84 组**静态基线，登记于 `ui-pages` §8（A 高危 2 页 × 5 静态态 / B 协作 9 页 × 4 态 / C 基础与设置 14 页 × 2 态 / D 组件外壳 5 个 × 2 态），A 档 S4 转交互对拍断言；采集须固定设备与 DPR，权限态须 `adb shell pm revoke` 重置后复采，采完人工过目签字方可作 `P4` 对拍基准。③ 成本：AI 施工护栏与验收基建由 +8–13 修正为 **+11–19**（含 84 组采集与签字 3–6），`P0` 16–26 → **19–32**，合计 257–379 → **260–385 人日**。

**AI 洞察**：

- 「250ms spring」是跨框架语义混写的典型形态：字面读起来完整，在一个框架里可实现、在另一个框架里无对应参数。跨框架迁移时，规范里每个时长与曲线都要问一句「目标框架里这个参数存在吗」——否则落地时必然变成 AI 自由发挥。
- 分母错误比状态定义错误更贵：状态矩阵按估计页数建，漏掉的是整类界面（本次漏 10 个协作页 + 5 个组件外壳 = 30 组），且漏采的恰好是协作域（E2EE 与断连态）这类最易出静默失败的地方。
- 瞬时态混进静态基线是最隐蔽的假阳性源：采图脚本每次都在不同像素上触发「长按呼吸态」，基线与比对都没有稳定语义，只产噪声 diff。
- 数字纪律：状态矩阵由草案 60 组修正为 84 组后，采图工期从「2–3 人日」修正为 6–9 人日（采集器 2–3 + 采集与签字 3–6）。**估工随事实修正，账要跟着改**——否则排期又是一张空头支票。
- 本轮还暴露一个文档级通病：同一件事在四五个章节各写一遍（页数、成本、门禁口径），改一处要同步五处，是口径漂移的温床。后续新增章节时应优先「引用既有 SSOT」而非复述数值。

### [2026-11-11] 转原生 Android：原生工程地基五项定案 (src: 用户)

**场景/痛点**：前三轮把规范、契约、AI 规程与防线封严了，但方案仍只覆盖「照规范重画」的工时，缺五项让原生工程**真能跑起来**的接入地基——存储层与既有 sqflite 库的兼容、依赖注入与对象图、页面路由契约、后台保活与 Android 14/15 强监管、进程冷启动时序与 MCP 初始化隔离。五项的共同特征是「不写进代码就会在第一次真机运行时崩」。

**可选方案**：

- 存储用 Room + 注入 `room_master_table` 的 `identity_hash` → **否决**：hash 随 schema 变化而变，手工注入脆且每次 schema 变更都要重做，与「既有库零迁移」前提相冲突。
- 存储用 `SQLiteOpenHelper` / SQLDelight（不引 Room 校验层）→ **采纳**：`lib/data/` 仅 5 文件 1,883 行且已有 `storage.dart` 存储抽象层，替换实现成本低；Dart `int` 是 64 位有符号，Kotlin 侧 64 位列强制 `Long`——`created_at` / `updated_at` 等为毫秒级、当前约 1.76e12，`Int`（上限 2.147e9）**必然**溢出，不是「万一超过」。
- DI 用 Hilt → **否决**：kapt/ksp 注解处理与代码生成负担，与「迁移期每加一个依赖都要评估构建链」的 R6 风险相悖；Koin 亦属新增依赖。
- DI 用纯 Manual DI（`AppContainer`）→ **采纳**：零注解处理、零生成代码、可在无 UI 进程独立构造（与启动分层同构）、单人维护零学习成本。
- 路由用字符串拼接 → **否决**：与魔数纪律同类，参数类型不安全。
- 路由用 Type-Safe Navigation → **采纳**，但补三条边界：浮层族不进 NavHost（保返回键逐层消费，见丢失点 #8）、返回结果走 `SavedStateHandle` 不引入全局事件总线、**当前无 DeepLink 与外部唤醒导航需求**（MCP 工具面无「打开某页」），故只登记契约不预建 deep link 基建。
- 后台保活照搬 Flutter 插件行为 → **否决**：Android 14+ `foregroundServiceType` 未声明即 `SecurityException`；Android 13+ `POST_NOTIFICATIONS` 未授权则通知不可见；Android 12+ 后台启动 FGS 受限；过夜日切需精确闹钟与电池白名单。
- 后台按 `dataSync` 类型长期常驻 → **否决**：Android 15 对 `dataSync` 类 FGS 新增 6 小时 / 24 小时配额，MCP 是长期常驻服务，必须选 `specialUse` 或 `connectedDevice`。
- 冷启动在 `Application.onCreate()` 全量初始化 → **否决**：MCP 被宿主 bind 拉起时必然先跑 `Application.onCreate()`，重初始化会吃掉 §4 R5 的 5s ready 预算并直接违约 `-32000`。

**最终决定**：五项写入 §9 工程基建表，各带判据与硬约束——① 存储不引 Room + 64 位列强制 `Long`；② 纯 Manual DI `AppContainer`，禁 Hilt 与多套混用，ViewModel 禁无参默认构造；③ 类型安全路由 + 三条边界；④ 后台服务规格（`foregroundServiceType` / 通知权限 / 精确闹钟 / 电池白名单 / 规避 `dataSync` 配额 / 保留 Doze 持锁结论）；⑤ 启动时序分层（Core 与 UI 隔离，延续 §11「`mcp_binder_entrypoint` 独立装配不经 `AppServices`」）。同步 §8 `P1` 与 `P3`、§9.1.2 禁止清单加两条（64 位列用 `Int` / DI 混用与默认构造）、§10 决定 7、schedule-app §11 新增「原生工程地基五项」行。成本第四次上修 +9–14 人日（`P1` 13–20 / `P2` 76–108 / `P3` 22–34 / `P4` 128–188），合计 260–385 → **269–399 人日**。

**AI 洞察**：

- 五项地基的共性是「**第一次真机运行时才暴露**」：编译能过、单测能绿、模拟器能跑，但 Room 校验崩、`Int` 溢出崩、`SecurityException` 崩、5s 超时违约。这类风险无法由「照规范重画」的工时覆盖——**初版估算只算了重画，没算让原生工程跑起来的接入成本**。
- 「必然溢出」比「可能溢出」的写法更有约束力：`created_at` 是毫秒级这件事就写在 schema 注释里（`lib/data/db.dart` 的 `-- 毫秒时间戳`），但跨语言映射时没人会去看那行注释，直到某天 `Int` 静默截断。跨语言迁移的必查项是**列语义**（宽度 / 单位 / 有无符号），不是列名。
- 启动时序不是新发明，而是**把既有事实写进规范**：Flutter 侧早已用「`mcp_binder_entrypoint` 独立装配不经 `AppServices`」解决同一问题（`app_services.dart` 的 bootstrap 串行做 DB 打开、远程配置加载、日切扫描，全是重量级 I/O）。既有分离若不写进 Kotlin 侧规范，AI 重写时极易「顺手统一」——把两个入口合成一个。
- 成本连续四轮上修（242–353 → 269–399，+11%–13%）的性质要说清：**不是估算失准，是范围认知在补全**，每一轮都对应一类此前没进账的工作（像素基线基建、AI 护栏、地基接入）。若要一次做对，唯一可靠办法是把「真机跑起来」当成 `P0` 的验收项，而不是 `P4` 的终点。

### [2026-11-11] 转原生 Android：Day-2 长期开发与发布运维规范定案 (src: 用户)

**场景/痛点**：`P0`–`P5` 覆盖的是「把旧功能跑起来」，而迁移完成后 1–3 年的新功能迭代（V1.5 候补：通知提醒 / 日历拖拽编辑 / 周月视图 / Markdown 导出；协作域后续阶段）才是长期主战场。若不定纪律，每加一个功能就长出一套新写法，最终再腐化一次——等于用 12–18 人月换来一个「换栈但没换质量」的工程。

**可选方案**：

- R8 规则交给「各依赖自带的 consumer rules」→ **否决**：实测 `goodhub-mcp-plugin-core` 0.1.0 / 0.1.1 / 0.2.0 三个版本 AAR **均未随包分发 proguard / consumer rules** → AIDL 接口类被混淆即跨进程 `RemoteException`（找不到类）；该缺陷在 SDK 仓不在本仓，应用侧必须自带 keep 兜底并推动 SDK 仓补发。
- 「Debug 包代表发布质量」→ **否决**：R8 只在 Release 生效，Debug 全绿与 Release 崩溃之间没有中间态信号。
- 上十几层微模块化 → **否决**：单人维护 Gradle 成本过高。
- 三层模块图（`:core:tokens` / `:core:model` / `:app`）→ **采纳**，并加一条本项目特有的硬约束：`:core:*` 必须是 **pure JVM 模块**（非 Android library），否则 12,408 行纯逻辑测试的 Kotlin 移植版只能跑仪器测试（慢一个数量级）；且**存储实现留在 `:app`**——`lib/data/storage.dart` 的既有存储抽象正好作为 core 层接口，SQLite 属平台层。
- 异常收敛只靠 `Thread.setDefaultUncaughtExceptionHandler` → **修正后采纳**：该 handler 只做崩溃记录与上报，**不防崩**；真正防崩靠结构化作用域（`SupervisorJob` + 统一 `CoroutineExceptionHandler`）与 `rememberCoroutineScope()`（Composable 内裸 `CoroutineScope(Dispatchers.IO)` 会泄漏并可能直接杀进程）。另补本项目专属的**异常分类表**：可预期异常降级为机器可读拒绝码（§10 铁律「拒绝码逐位不变」属契约），不可预期才允许崩。
- 另核实：`lib/main.dart` **无** `runZonedGuarded` / `FlutterError.onError`，`lib/` 全库**零反射**用法 → 「告别 Dart Zone」是通用最佳实践而非本项目现状平移（Kotlin 侧属新增能力）；反射面只剩 protobuf 与 kotlinx.serialization 两条官方规则覆盖的路径。
- 设计系统只搬令牌 → **否决**：只搬数值等于把「每个新页面重写几十行 Modifier」的问题原样保留。
- 设计系统三层（令牌 → `ShiguangTheme` → `Shiguang*` 原语组件）→ **采纳**，并补关键定位：原语组件是**丢失点的一次性修复**（安全区、48dp 触控区、IME 避让、逐层返回拦截、浮层 Z 序内建）→ 新页面自动继承合规；同时明确组件库是 `P4` 的**收敛产物**（规范 → 组件 → 页面），不得反向成为生成通道输入源（否则与 §8「输入源权威性闭环」形成循环）。
- Day-2 流水线照搬通用四步 → **修正后采纳**：本项目 Dart 侧本就是「命令面 + 查询 + 状态订阅」三层，Day-2 流水线是**既有架构的 Kotlin 表达**而非新发明；每步对应既有机械门禁（向量对拍 / 单写队列 / 像素 diff / arch-guard-kotlin + Konsist）。

**最终决定**：五项写入 native-migration §9 表（构建与混淆 / 模块图与依赖边界 / 异常与日志纪律 / 设计系统组件库），并新增 §11「Day-2 长期开发与发布运维规范（迁移完成后沿用）」——11.1 新功能四步流水线 + 机械门禁卡口、11.2 迁移后黄金向量来源变更、11.3 发布纪律、11.4 编译速度守护、11.5 日志与隐私。§9.1.2 禁止清单加三条（Release 日志泄露 / Composable 内裸协程作用域 / 依赖「官方应该带了」混淆规则）；§8 `P4` 施工序①改为设计系统三层；§10 新增决定 8；schedule-app §11 新增「Day-2 工程纪律五项」行。成本第五次上修 +8–13 人日（`P3` 24–38 / `P4` 132–194 / `P5` 13–20），合计 269–399 → **277–412 人日**。

**AI 洞察**：

- §11.2 是这一轮最易漏的深水区：`P5` 前黄金向量的期望值由 **Dart 侧实现**生成（双实现对拍），`P5` 后 Dart 侧退场，期望值只能人工构造——**对拍退化为「Kotlin 实现 vs 人工期望值」**，「对拍自证闭环」的风险在迁移后不降反升。这个风险藏在「迁移完成了」的喜悦里，越完备的迁移方案越容易把它盖住。
- 「Debug 跑通 ≠ Release 可用」在本项目有具体载体：AIDL 跨进程面 + E2EE Provider + 序列化实体三条都只在 Release 被裁剪或混淆，且**全是静默失败**（找不到类 / 算法不可见 / 参数反序列化失败），与 §4 R1 / R5 的失败模式同族。
- 模块化的真正判据不是「几层」，而是「**core 层能否不碰 Android 就跑单测**」。本项目有 12,408 行纯逻辑测试这口金矿，若 `:core:*` 用了 Android library，移植后的单测就得跑仪器测试——几千用例 × 每次真机部署，才是编译与测试速度的灾难。
- 五轮评审的共同形状是「**在写代码之前先发现写不出正确代码**」：从契约 → AI 规程 → 工程地基 → 运维纪律，每轮都在把「会崩的地方」提前变成「会写进文档的地方」。成本连续上修到 277–412（+14%–17%）买的不是工期，是**把腐化推迟到有对策的时候**。

### [2026-11-11] 转原生 Android：执行定位定案（Spec-Driven Refactoring）与禁飞区收敛 (src: 用户)

**场景/痛点**：六轮评审的最后一轮给出总纲——把迁移定义为「以规范为准绳的架构级重构」，并明确**开刀区**（可趁机彻底重构的部分）与**禁飞区**（必须冻结的外部可观察行为）。这轮意见约 85% 已被前五轮落盘内容覆盖（设计系统组件化 / 并发事务 / 时钟触发 / 契约冻结 / 手势阈值冻结 / 两通道输入 / 双重验收），真增量三处半。

**可选方案**：

- 逐行直译 → **否决**：旧框架妥协与过期 workaround 原样搬入新栈，Day-1 就背上「原生外壳、Flutter 灵魂」。
- 推倒重来 → **否决**：第二系统综合症，工期无限延期。
- Spec-Driven Refactoring（开刀区重构实现结构 + 禁飞区冻结可观察行为）→ **采纳**。
- 禁飞区仅列「业务规则与拒绝码 / 通信契约 / 手势阈值」三块 → **否决**：漏了本项目最硬的 **E2EE 封装字节**（§4 `R1` 头号静默失败对象）、**DDL 与 Schema**、**64 位列语义**三块。
- 调度器只规定「写事务单线程」 → **修正后采纳**：补 `Dispatchers.IO`（网络与磁盘读）与 `Dispatchers.Default`（纯计算与加密——Argon2id 派生与 E2EE 封装解封属 CPU 密集，放 IO 会占满磁盘池并饿死网络请求）的分工，并禁 `GlobalScope`。
- 允许「事件回调里再查一次 repo」的反向拉取 → **否决**：Flutter 侧 `Listenable` 只发「变了」的通知（实测 17 个订阅点），反向拉取是既有写法；不显式禁掉，它会在 Kotlin 侧复活成「StateFlow + 局部 setState」混合体，State Hoisting 形同虚设。

**最终决定**：① §1 结论补「执行定位：Spec-Driven Refactoring」声明 + 开刀区 / 禁飞区对照表（**导航层，非新约束**）；② §9 表新增「协程调度器分工」行，并把「状态流转终态（只读 `StateFlow` + 禁反向拉取）」并入「对象图与 DI」行；③ §9.1.2 禁止清单新增两条（反向拉取 + 局部可变状态副本 / 迁移期禁飞区四类）。**成本不变**（277–412 人日）——本轮全是规范表述与边界澄清，无新增工程量。**不再新增章节**：前五轮已把契约、AI 规程、工程地基、运维纪律分列 §9 / §9.1 / §11，本轮作为索引与收口处理。

**AI 洞察**：

- 这是六轮里唯一一轮**大部分内容是重述**——恰恰说明前五轮落盘是完整的：AI 施工规程、工程地基、Day-2 运维各自成节，禁飞区散落在 §10 铁律与 §9.1.2 禁止清单里。本轮的价值不在新增条款，而在给这些散落的边界**画一张地图**。
- 六轮收敛轨迹值得记：契约 → AI 规程 → 规格补缺 → 工程地基 → 运维纪律 → 执行定位。前三轮解决「写什么」，第四五轮解决「怎么落地才不崩」，第六轮解决「凭什么敢重构」。最后一轮永远是**定位**而非细节——定位错了，前五轮的细节全部作废。
- 「禁飞区」比「禁止清单」更贴切：前者说的是**重构的合法边界**（不是「AI 不许做」，而是「这个项目在迁移期不许动」），后者是给 AI 的行为约束。两者都必要，但前者是对人的承诺——一旦写进文档，未来任何一次「顺手优化」的冲动都要先撞上这张表。
- 成本连续五轮上修后本轮归零，是健康信号：文档已从「补需求」转入「收边界」。下一轮不该再有新增条款，应该转入**执行**——否则继续评审只是在给同一份文档加注释。
