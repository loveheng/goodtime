# 背景信息记录（Background Context）设计草案

> **状态**：**定稿已批施工**（2026-10-07 用户开工指令；拍板留痕=schedule-app §11「背景信息记录（backgrounds）」行）。2026-10-06 起草；**2026-10-07 定稿收敛**（外部评审核实后 Q1–Q5 全部决议、模型定稿）。
> **核心命题**：拾光处理两类用户零散输入——**硬事实**与**软背景**，必须分清，否则会把软偏好变成硬墙，违背 §13 反压迫条款。
> **关联**：主草案 = `fact-user-relay-draft.md`（事实挂载/摄入管道/随行凭证 UI，2026-10-07 收敛）；本草案是主草案 §1.6 三刀路由的第④去向（兜底）；多人预留原则见主草案 §3.4。

## §1 定位：背景信息 ≠ 事实

| 维度 | 事实（Artifacts，见主草案 §1） | 背景信息（Background） |
|---|---|---|
| 性质 | 硬约束：时间/空间锚定的客观凭证 | 软上下文：叙事性、定性的行程背景 |
| 例子 | 车票车次、检票口、闭馆日、需带身份证 | 「陪父母看诊顺带旅游」「妈妈膝盖不好少走路」「上次大理高反严重」 |
| 对排程 | 刚性边界，引擎强制（pinned / 硬红线） | 柔性提示，仅影响 AI 软提案权重 |
| 结构化 | 强结构 JSON（anchors / constraints） | 弱结构：自由文本 + 可选标签 |
| 主要读者 | 排程校验器 + AI | 主要 AI（带理由提案时参考） |

**一句话区分**：事实是「引擎必须遵守的规则母体」；背景是「AI 应记在心里的上下文」。

## §2 数据模型（✅ 定稿，2026-10-07）

**独立 `backgrounds` 表（Q1 ✅）**，与 artifacts **同批 schema v3 迁移**（一次迁移、两张表）。**2026-10-07 施工时序调整**：背景侧先行开工 → backgrounds 先行 v3 单表迁移；fact 草案同日拍板（§0 七项通过），artifacts 定为 **v4** 另批迁移（主草案 §1.1/§8 已回改，schedule-app §11 留痕）。

```
backgrounds(id, scope, plan_id?, content, raw_source_text, tags,
            applicable_dates, source, captured_by, created_at, updated_at, version)
```

字段规则：

- **机读/展示分离原则同 artifacts**：`content` 是给人与 AI 读的归纳描述；`raw_source_text` 永存原话（溯源/撤销重构）。
- `tags` = 自由字符串标签（#健康 #偏好 #历史 #目的 #环境…），**不锁闭枚举**——用法靠 AI 使用纪律约束，真需要机读的那天再收敛枚举。
- `applicable_dates`（可空，TEXT 列存 JSON **单日 ISO 日期字符串数组**，如 `["2026-10-08","2026-10-09"]`；SQLite 无数组类型，JSON-in-TEXT 惯例同 open_items/exceptions）：瞬态背景的作用日期窗（脚扭伤/经期/雨周）；缺省=长期有效。比对=集合成员判断（当日 ∈ 数组），零语义、可测试。**长窗劝改**：日期窗超过约 14 天时 AI 应建议改为长期背景（去掉日期窗）——瞬态窗本就该短，长窗说明不是瞬态信息，防数组膨胀。主要风险面在 scope=global（plan 级背景天然随行程结束失活）。**入库校验与规范化（施工钉子）**：逐元素**双检**——正则 `^\d{4}-\d{2}-\d{2}$` + `DateTime.tryParse` 回写比对（纯正则挡不住 `2026-02-30` 非法日历日）；**空数组写入口归一化为 null**（「永不生效」是陷阱态，语义=长期）；去重+排序（集合判断与「过去的背景」折叠比较需稳定序）；读侧防御——畸形元素逐个过滤并留 `[DEGRADE]` 日志（静默吞违反副作用纪律）。校验单点=命令层 UpsertBackground（human 日期选择器天然合法，AI 是防守对象），工具描述同步写明格式。
- `source` = `user | ai_derived`（provenance，支撑「AI 提炼可追溯」）。
- `captured_by`（DEFAULT 'me'）= **多人预留钉子**（主草案 §3.4：roster 落地后回填真实身份）。
- `version` 乐观锁——仓库纪律（字段级 patch + CAS，plans/blocks 同款），外部评审稿漏了此字段，已补。
- **延后不预置（多人轨，主草案 §3.4）**：`privacy_level`（MVP 全本地无第二态）、`ai_visible`（删除即不可见）、`is_deleted` 墓碑（单设备真删）、`created_by`/`subject_ids`。
- **Q1 论据纠错**：独立表成立的**本地理由**是行级增删改干净 + plans 表不撑肥 + 与 artifacts 同批迁移；外部评审的「LWW 丢数据」论据不成立——仓库是 CAS+快照重试，不会静默丢，只是数组字段的合并负担难看。
- **外键与删除处置（仓库口径：外键 NO ACTION 做护栏，删除处置归命令层）**：`plan_id REFERENCES plans(id)` 不带 ON DELETE（与 plans.parent_id / blocks.plan_id 同款）。`delete_plan` 命令**同事务显式级联销毁**该 plan 名下全部背景（语境随本体消亡，物理删除不留孤儿）。**否决 DDL 级 `ON DELETE CASCADE`**：外键在本仓是「未处置引用让删除硬失败」的护栏（`_deletePlan` 现将 FK 异常转为带指引的拒绝），静默级联会绕过命令层处置语义。

scope=global 的**注入预算**：全局背景条目 ≤8 条、总量 ≤400 字（阈值常量入 rules 单一出处，与填充率同款管理）——防上下文稀释的机械刻度（§4 纪律二）。

**预算执行 = 命令层机械拦截，非 AI 自觉**（对齐「机械校验非 AI 自觉」拍板，与填充率红线同模式）：

- **终态校验统一式**：任何写操作（单条或批量）落库前评估**最终状态**——`终态条数 > 8 或 终态总字数 > 400 → budget_exceeded 整体拒绝`。「5 条时插入 250 字长段」与「直接写第 9 条」是同一规则的退化情形，无两套逻辑。
- `CommandActor.ai` 命中 → hint「发起归并询问后重试」；**拒绝体 data 直接附当前全局背景全量摘要**——AI 无需重读即可提出具体归并方案（「这次提到的『常住深圳』建议与之前的『珠三角周末游』合并，你看可以吗？」），照抄 `version_conflict` 回 latest 快照、`schedule_rejected` 回空窗的返回契约风格。
- **归并走原子批处理命令**：ops 数组（删 A / 删 B / 插 C）单事务执行、终态校验全过才落库、否则整批拒——防「先插 C 再被拦」死锁与「先删 A」有损中间态；模式先例=`update_fixed_slots` 整批原子替换 + `propose_schedule` 按天整单原子写 + FIFO 写锁串行。批命令 human 同样可用（app 内手动归并同通道）。
- **human 通道放行**（校验刻度不对称：人可以任性，AI 必须讲理）——用户在 app 内手动添加永不被拦，至多温和提示。
- plan 级背景**不设预算**——plan 作用域天然随行程终结，只有 global 需要卡口。

**度量口径（施工钉子，2026-10-07）**：①**计算单点=命令层**（Dart `String.length`，UTF-16 码元；SQLite `length()` 不在执行路径——中文场景码元≈码点，确定性优先于语言学纯洁，不值得换 `runes`）；②**只计 `content` 字段**——`raw_source_text`（溯源存证，只增不清）与 `tags` 不进分子，堵「往 raw 塞长文绕预算」的暗门；③常量（8/400）入 rules.dart 单一出处（与填充率同款管理），`upsert` 工具描述与 playbook 写明「content 总字数按字符计 ≤400」——AI 能自测才不会反复撞墙。

## §3 捕获 UX（✅）

- **入口 1：计划详情「背景」区** —— 与「随行凭证」（主草案 §2）并列的分区，用户随手记。条目卡右上角轻量**日期角标** `[10.08–10.10]`（applicable_dates 派生渲染不入库，无日期窗不显示）；超期条目派生沉入「**过去的背景**」折叠组（与「过去的凭证」「收起的旧想法」同一收纳模式），清理动作在折叠组内（逐条删+批量清理），主列表不加清理图标降噪——角标自答「为什么 AI 排程没理会这条」（Q6 ✅）。
- **入口 2：快记 FAB 长文本 / 系统分享** —— 与事实同管道进入，经三刀路由（主草案 §1.6）无刚性时空边界、非行动类的兜底落背景。AI 提炼遵守**「捕获原子化，治理归并化」**：一条记录=一个可独立成立、可独立删除的语义（判据：能否单独删掉而不损义），严禁大段打包（200 字叙述拆为 1 条 #健康 + 1 条 #交通偏好分别落库——便于单独删除、单独挂日期窗，同时服务碰撞检出）；同主题同时效的归并只在治理时发生（与预算拦截的归并询问衔接）；整段倾倒时各原子允许引用同一段原文（raw_source_text 存相关片段，溯源不断）。
- **入口 3：AI 对话流提炼** —— **文本显式回显**（「已记录背景：妈妈膝盖不好——不对就说我改」）+ `raw_source_text` 溯源 + 详情页随时可删。**不设专门撤销 UI 子系统**（可消除 Chip）——对话回显 + 删除通道已覆盖同一需求，零新机制（Q3 ✅）。
- **手动编辑契约（入口 1 卡片编辑）**：改 `content` → `raw_source_text` **永不变**（保留最初原话作溯源证据链；AI 后续再提炼同条记录同样不得覆盖——raw 仅在 state raw→structured 时填一次）、`updated_at` 刷新、`version` 递增走 CAS。`source` **出生来源不可变**（user/ai_derived 不因后续编辑翻转——翻转=销毁「曾由 AI 提炼」的溯源，恰破坏本契约要保护的证据链）；「最后编辑者」语义归多人轨（主草案 §3.4 预留清单）。

## §4 AI 消费方式（✅ + 两条纪律）

- 背景（`scope=plan` 的随涉事 plan 快照、`scope=global` 的按预算常驻）作为**软上下文**注入，与 `identity_prompt`、`spec` 并列。
- **双通道装配（✅ 2026-10-07 补，机械过滤非 AI 自觉）**：**排程装配物理过滤**——装配器做 `当日 ∈ applicable_dates` 集合判断（无窗=恒注入），超期背景**根本不进排程上下文**（省 token + 杜绝「用过期的脚扭伤排今天徒步」的幻觉）；**治理/对话装配全量带标**——超期项带 `[已过期]` 标记下发，AI 可发起「『脚扭伤』已过期，顺手清理？」建议（衔接 §2 归并询问）。日期窗过滤是确定性集合运算（与管家日切扫描同性质），非第二个智能，不违反单解析器铁律；落点=queries 装配层（get_settings 携全局背景+预算态、plan 快照携 plan 背景，均既有搭载模式）。
- 仅影响**提案权重与理由**，不生成硬约束；提案理由区须显式引用背景（「因背景提及高反史，已预留氧气购买缓冲」）——可解释性实践，反压迫条款「提案附理由」的素材源。
- **多计划分区装配（✅ 2026-10-07 补）**：单日涉多计划时，背景按计划**分组注入、严禁平铺混排**——装配器输出分组载荷（global 段 + 各计划段，每段带 `scope_note: "仅约束该计划下的活动块"`），AI 在生成某计划的块时只读自己那段（商务「全天紧凑」绝不吃到家庭段的「保证午睡」）；**日级态势句不携带任何背景**（容量/天气是几何机械数据，混入叙事徒增串味面）。领地纪律一句：**硬事实切时空领地（重叠校验/pinned 硬墙，机械），软背景只在各自领地内定松紧**——多计划并发的隔离成本就这一条条款，零 schema 零命令。
- **祖先链继承**：注入范围 = 计划自身 + 祖先链（≤3 级，与粒度定律深度一致）。反例踩中即证必要：金样本 #4 的 bg_knee 挂 p1 根计划、块在 c4/c6——若字面执行「只注入涉事 plan」，膝盖背景永远到不了旅途块。与资料箱子树派生聚合对称：同一语义，显示面聚合、推理面沿父链注入。
- **特异性优先（✅ 2026-10-07 补，背景专属软政策）**：祖先背景是泛化默认，当前计划/叶子背景是具体细化——**局部范围差异以当前计划为准**（「爬山日可走陡坡」覆写当天的「少走陡坡」，因范围就是这一天这一件事）。落点双轨：装配载荷在祖先背景实际参与时携带**静态常量注记** `inherit_note:"祖先背景为泛化默认；当前计划背景为具体细化，局部差异以当前计划为准"`（确定性字符串零智能；单层不携带防噪音）+ playbook 写完整规则。**分界线**：特异性优先只管「范围细化」（更窄范围覆写泛化默认），**真正互斥矛盾仍走纪律一澄清**——不许拿「特异性」当静默折中的借口；覆写发生时提案理由区必须注明「叶计划背景优先于全程默认」（溯源纪律延伸，用户始终看得见哪条赢了）。本条**不外溢 artifacts**——constraints 是票务事实绑定，不存在继承。
- **纵深与边界**：串味防线三道——分区装配（机械，第一道）→ 理由精确溯源（AI 引用哪条背景可见，第二道）→ 分级确认卡（人终审兜底）；**不做「AI 使用了哪条背景」的追踪**（伪遥测，与去向标记诚实口径一致）；plan 级背景**不加第二道预算卡口**（全局预算已足够，原子化捕获约束条目膨胀，观察即可）。
- **纪律一「碰撞即澄清」**：发现互斥背景（「想越松越好」vs「一天打卡全部地标」）必须先经既有澄清管道问清，**严禁静默折中**——折中平庸/精神分裂提案的防线是政策不是机制。
- **纪律二「注入预算」**：**不建标签相关性召回层**（第二个智能判相关性违反「AI=唯一推理」铁律，且 plan 级条目量级为个位数，不值得建检索系统）——场景相关性由作用域结构解决：排某天只读当天涉事 plan 的背景，全局背景靠预算卡口（卡口由命令层机械执行，见 §2 预算拦截；AI 被拦后发起具体归并询问，治理责任不推给用户主动翻查）。
- **三通道全局路由（Q2 ✅）**：人设/语气 → `identity_prompt`（settings 既有键）；硬性常驻规则（「周五晚上不排深度工作」）→ `user_rules`（既有键）；常驻画像叙事（过敏原/常住地/随行成员常态）→ `backgrounds(scope=global)`。**不加第三个 settings 键**，路由表进 playbook。

## §5 与事实体系的边界（✅ 维持）

判据：**该信息是否产生刚性时空边界？**（即主草案 §1.6 三刀路由的第①问）

- 「玉龙索道 10:30 进闸」 → **facts**（硬时间锚）。
- 「这次主要看雪山，体力有限」 → **background**（软偏好）。
- 灰色带（如「建议提前 45 分到场」）→ 可同时落：facts.constraints.advance_arrival_minutes（硬派生缓冲）+ background 叙述（让人懂为什么）。

多用户下（中继轨）：background 同样可 `shared_scope`（public 团队背景 / private 个人健康隐私）；健康类背景默认 private（呼应主草案隐私分级），`privacy_level` 字段随中继轨补列（主草案 §3.4）。

## §6 隐私与同步（✅ MVP 口径 + 中继轨挂账）

- **MVP 全本地**：一切背景天然 local_only（§13「现实后花园」、零遥测），无隐私字段可设。
- 多人/中继落地时（主草案 §5/§6，**规划中的后续阶段**）：`privacy_level(local_only | e2e_synced)` 默认 local_only；健康/医疗/财务类条目 AI 提示用户保持本地；private 项同步时本地剥离。字段延后不预置。
