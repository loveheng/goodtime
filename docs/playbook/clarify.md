# clarify —— 澄清流程（playbook）

> 上游：[schedule-app.md](../design/schedule-app.md) §7（澄清收敛阈值/最小澄清原则/reward_spec）+ [functional-spec.md](../design/functional-spec.md) §1 M3。本文件是 MCP prompts 与分发 SKILL 的内容源（同源不分叉）。

## 何时澄清

- 排程前必须到达**明确态**：spec 非空且精确 + open_items 为空。
- 有未决 open_items 先澄清再排（软政策：允许先排已确定子任务）。
- **最小澄清原则**：估算 ≤30 分钟或性质平凡（购物/琐事类）**免除澄清**，直接生成叶子行动——琐事配得到的是一次被排上日程，不是三连问。

## 问答次序

1. 单轮最多追问 **2–3 个问题**，按「**先时间后细节**」排序（什么时候/多长 → 细节）。
2. 用户连续两次回答「不知道/不想定」的项，**不得继续追问**——提取最小可执行单元强行推进到明确态，未决内容记入 notes 备注待定。
3. 澄清是管道，不是审讯。

## spec 写作规范

- 精确无歧义：时间、地点、对象、产出物写死；「待定项」显式标注而非模糊化。
- 动词开头、一次能做完。
- 确定型长任务在 spec 尾部追加**路线图块**（语法见 decompose.md）。

## 犒赏收尾（付出型限定）

- 高阻力计划判定：importance=true 且预估总耗时 ≥180min（学习/项目/筹备/家务）。
- 澄清最后一个问题固定为：「**这仗打完，准备怎么犒赏自己？**」→ 答案落 `reward_spec`。
- **纯休闲享乐类（玩/吃/逛）天然自犒赏，跳过收尾问句**——对逛街问「怎么犒赏自己」是反效果的怪问题。
- 未兑现的 reward_spec 永不催促，仅自然时机温和重提。

## 多人可用性假设标注

拾光单用户，AI 永远看不见第三人的日程。凡澄清涉及他人时间（家庭活动/约会/接送）：
- 显式标注「**该空闲系用户口述**」并建议临行前口头复核；
- 家人可用性只有三条输入通道：澄清问答、共享日历投影（若可读）、用户手工 human 块。
- 朋友类活动同规则且更弱：协调在 app 外（IM）进行，拾光只记「我的时间承诺」这一侧。
